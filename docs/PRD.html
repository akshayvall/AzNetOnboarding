1. What a PRD is (and why this one exists)

Teaching note: A Product Requirements Document is the single source of truth that answers four questions before anyone builds: who is this for, what problem does it solve, what it must do, and how we know it worked. It is not a design doc (the "how it looks") or a tech spec (the "how it's coded") — it sits above both so engineering, design, and stakeholders share one intent. Each section below maps to one of those questions.

This PRD documents an already-built, production-complete product. That makes it a "reverse PRD" — written to (a) capture the product's intent in one place, (b) anchor the next change (removing exam-alignment framing), and (c) serve as the reference for future iterations. Reading it top-to-bottom should give a complete mental model of the product without opening the code.

2. Executive summary

Azure Networking Academy is a browser-based, offline-capable learning platform. It teaches Azure networking as a structured journey across three difficulty tiers (L100 Foundations → L200 Intermediate → L300 Advanced), spanning 21 modules. The product favors doing over reading: animated diagrams, interactive tools (subnet calculator, flashcards, drag-and-drop), per-module quizzes, and copy-paste Azure Cloud Shell labs.

It is deliberately dependency-free: vanilla HTML, CSS, and JavaScript — no frameworks, no build step, no external network calls. It runs by opening one file and ships to the public web via GitHub Pages. A distinctive trait is its heavy emphasis on Azure Front Door (AFD) — roughly three to four modules — reflecting real-world edge-delivery, CDN, WAF, and routing scenarios.

3. Problem & opportunity

Why this section: If you can't state the problem crisply, you can't tell whether the product solved it. This is the "why build it at all" anchor.

The problem

  • Fragmented learning. Azure networking knowledge is scattered across docs, videos, and exam guides. Learners lack a single guided path from "what is a subnet" to "design a hub-spoke topology."
  • Passive material. Most resources are read-only. Networking concepts (CIDR math, traffic flow, NSG evaluation order) are best learned by manipulating them, not just reading about them.
  • Tooling friction. Many tutorials require an account, an install, or a live subscription before the first concept lands.
  • Exam-shaped, not skill-shaped. Material framed around a certification optimizes for passing a test rather than building durable, transferable networking intuition.

The opportunity

A single, zero-friction, interactive app that sequences the full Azure networking story, teaches through interaction, runs anywhere (even offline), and is framed around real-world skills and architecture — with a sharp practical lens on Azure Front Door.

5. Goals & non-goals

Goals

  • Take a learner from networking fundamentals to advanced Azure architecture in one coherent, ordered path.
  • Teach through interaction — diagrams, calculators, quizzes, and hands-on labs — not passive text.
  • Run with zero setup: open in a browser, work offline, no account, no install.
  • Give Azure Front Door first-class, in-depth coverage (config, caching/performance, WAF/security).
  • Persist learner progress locally and let them export/import it.
  • Frame all content around durable, real-world networking skills.

Non-goals

  • Not a certification exam-prep product. (This is the explicit repositioning in §9.)
  • Not a live lab environment — labs are copy-paste recipes for the learner's own subscription, not a sandbox we host.
  • No backend, accounts, or telemetry. Progress lives in the browser only.
  • Not a replacement for official Microsoft Learn docs; it complements them.
Why non-goals matter: Naming what you won't do prevents scope creep and sets reviewer expectations. A non-goal is a decision, not an omission.

6. Curriculum structure

Three tiers, 21 modules, sequenced so each builds on the last. The progression mirrors how a network engineer actually learns: fundamentals → core Azure services → advanced design.

8. Technical architecture

Teaching note (for a beginner coder): "Dependency-free" means the app uses only what the browser already provides — no React, no npm packages, no build/compile step. The upside: it's trivial to run, audit, and will still work years from now. The trade-off: you write more by hand. For a learning tool meant to last and be trusted, that trade is the right call.

⚠️ Security rationale

A strict CSP plus zero external calls means no third-party script can run and no learner data leaves the browser. The threat it prevents: supply-chain or injection attacks via external dependencies, and inadvertent data exfiltration. For a tool that may run inside corporate environments, that posture is a feature.

9. Repositioning — de-coupling from exam framing

🎯 The change this PRD authorizes

Remove all certification-exam ("AZ-104 aligned") framing across the product and reposition it as a real-world Azure networking skills platform. The pedagogical content stays; only the exam-shaped wording, callouts, names, and links change.

Why

Exam alignment narrows the product's perceived value to "test prep" and dates the content to a specific certification version. Reframing around durable skills broadens the audience, ages better, and matches the actual depth of the material (which goes well beyond any single exam).

10. Success criteria

Why measurable criteria: "Done" must be testable. Each line below is a check you can pass or fail — no judgment calls.
  • Zero "AZ-104" / exam-alignment references remain in any user-facing file (verifiable by a case-insensitive search returning 0 hits).
  • All 21 modules still load and render after edits (no broken markup or JS).
  • Every interactive feature (quizzes, calculator, flashcards, diagrams, labs) still functions.
  • Lab resource names are consistent (rg-net-lab / vnet-lab) across all CLI/portal blocks.
  • Renamed Module 15 retains all its lab/scenario content; only framing changed.
  • Product reads as a real-world skills platform end-to-end (tagline, README, callouts, links).
  • App remains dependency-free, offline, and CSP-strict (no new external calls introduced).
